# Точная поставка версии

Готовая публикация создаётся `scripts/build-platform-release.mjs` после Firebase, Career, Reception и обновления календаря. Исходный `site/` не переписывается генератором. Сборка принимает **фактически опубликованный** предыдущий архив и новый каталог staging, затем проверяет его до загрузки в Pages.

* Runtime HTML/JS/CSS: `/_releases/<buildId>/<исходный путь>`. Относительные импорты остаются внутри этой версии. Inline ES-модули HTML становятся соседними сгенерированными `.mjs`.
* Неизменённые данные и медиа сохраняют первоначальный путь и замороженные байты. `platform-baseline.json` хранит их контрольные суммы. Их нельзя заменять новой копией `site/`.
* Новые и изменённые данные: `/_objects/<полный SHA-256>.<расширение>`. `resourceURL()` сопоставляет логический URL с этими неизменяемыми байтами, в том числе без service worker.
* `release.json` указывает current и previous; в каждом immutable runtime есть собственный descriptor и проверяемый manifest. Build ID вычислен по конечным runtime-текстам с нормализованным собственным ID, хешам ресурсов и шаблону worker. При проверке он пересчитывается.
* Staging сохраняет current/previous runtime, необходимые объекты и замороженный baseline. Предельный размер — 1 000 000 000 байт. Просроченные runtime не включаются в следующую поставку; архивы GitHub не удаляются.

Полные HTML-входы отличаются от данных baseline: канонические адреса всех опубликованных игр становятся маленькими alias-страницами, которые читают текущий manifest и открывают соответствующий exact HTML. HTML-фрагменты остаются замороженными. Реестр baseline схемы 2 хранит исходные хеши исключённых входов отдельно в `legacyEntryHTML`; список вместе с замороженными файлами входит в baseline ID. Верификатор проверяет alias-страницы и корневой `404.html` побайтно. Это явное исключение первой миграции, а не изменение байтов данных.

В каждом полном HTML встроен небольшой recovery-скрипт без импортов. При холодном открытии устаревшего exact-адреса Pages 404 восстанавливает только известный публичный HTML по проверенному текущему manifest. Сохранённый браузером старый корневой HTML также восстанавливается при отсутствии его bootstrap или descriptor. Query, hash и `rudnResume` сохраняются; временный маркер `rudnRecovery` ограничивает переход одной попыткой и удаляется после запуска. Неизвестный путь остаётся 404, повреждённый текущий runtime не запускает цикл перезагрузок, уже работающая старая вкладка не перенаправляется. Этот путь работает без service worker и CacheStorage. Состояние задания при холодном запуске восстанавливается штатным хранилищем/координатором; recovery не создаёт новую попытку и не пишет ответы.

`prepareRelease()` проверяет оболочку и пакет активного модуля до переключения. Флаг `durable` означает возможность записать подготовленный пакет в CacheStorage; он не означает, что загружен весь корпус документов. Состояние пользователя сохраняет координатор отдельно в IndexedDB. `rudnResume` — случайный локальный идентификатор восстановления, без ответов и учётных данных. Если вкладка потеряла sessionStorage, bootstrap читает указатель из localStorage по этому идентификатору. После восстановления координатор удаляет указатель и query-параметр.

Версии интеграционных контрактов сохранения заданы в `site/data/platform-contracts.json` и включены в `manifest.contracts`: конверт обновления, snapshot адаптера, durable store и каждый модуль. Их JSON входит в build hash. Отсутствующий или некорректный контракт не допускается сборщиком и bootstrap; координатор проверяет совместимость до паузы активной работы. Это отдельные версии от внутренних правил игровых движков.

Worker не перезагружает вкладки. Он сохраняет их точные bindings, проверяет хеши сетевых ответов и сообщает координатору о новой версии. При ошибке раннего импорта/таймауте восстановления bootstrap допускает только одну попытку возврата на immutable previous. Событие `rudn:release-boot-failed` отменяемое: готовый координатор вызывает `preventDefault()`, если сам управляет восстановлением. `markReleaseRestored()` / `rudn:update-restored` снимают watchdog.

Первый переход со старой оболочки имеет `previous: null`: прежняя версия не поддерживает новый протокол snapshot. Открытая старая вкладка сохраняет свой кэш и замороженные lazy-ресурсы; её нельзя считать автоматически восстановленной новой системой. Со второго выпуска previous имеет проверяемый immutable manifest.

Уже сохранённый до первой миграции legacy HTML не содержит встроенного recovery, и задним числом добавить его в локальную копию браузера нельзя. При сетевом получении нового канонического HTML появляется новый протокол; автоматическое восстановление удалённых exact-входов гарантируется для выпусков, созданных этим сборщиком. Существующие legacy-вкладки не перезагружаются принудительно.

Проверка импортов начинается со всех публичных HTML, main и module entry, включает статические ES-импорты, строковые `import()` и `new URL('worker.mjs', import.meta.url)`. Неполные недостижимые исторические файлы перечисляются в `unreachableImports`. Например, старый Settlements v2/map.mjs ссылается на отсутствующий Leaflet, хотя действующий v24 его не исполняет. Этот список не разрешает пропуск отсутствующей зависимости достижимого приложения.

После успешного Pages deploy архив `platform-release-<buildId>.tar.gz`, SHA-256 и receipt сохраняются в GitHub Release; резервный Actions artifact имеет срок 90 дней. Следующая сборка выбирает baseline по build ID реально опубликованного `release.json`, а не просто по самому новому тегу. При отсутствии обоих архивов сборка завершается ошибкой. Для первой миграции единственный fallback — проверенный Pages run 39135557270; после появления exact pointer этот fallback закрыт.

Проверки протокола: `node --test scripts/test-platform-release.mjs scripts/test-platform-release-worker.mjs`; браузерная синтетическая проверка: `node scripts/test-platform-release-browser.mjs` с `PLAYWRIGHT_PATH`, `PLAYWRIGHT_BROWSERS_PATH`, `QA_OUT` при необходимости. Физические смартфоны — отдельная полевая проверка.
