# Нативная интеграция симулятора губернатора

Версия платформы: **1.3.1**. Версия приложения симулятора: **1.0.0**. Версия формулы: **`governor-assignment-v1`**. Код опубликован через [успешный выпуск GitHub Pages](https://github.com/Arseniy24RUS/RUDN/actions/runs/34642672669). Реальный вход преподавателя и доставка нового результата в действующий Firebase остаются неподтверждёнными.

## Маршрут и запуск

Страница курса `#activity/seminar-7` открывает относительный адрес `apps/governor/index.html` в том же окне. При размещении курса под `/RUDN/` адрес модуля — `/RUDN/apps/governor/index.html`. Возврат ведёт в `#activity/seminar-7`. Встраивания через iframe и чтения результатов внешнего симулятора нет.

Модуль использует существующие `backend`, `attemptOwner()` и `topicGate(7, …)`. До запуска он ожидает восстановления платформенной сессии. Гостю предлагается вернуться и войти в профиль курса; отдельной регистрации в игре нет. Для студента действует открытие раздела 7 по расписанию и переопределениям преподавателя. Прямой URL не обходит эту проверку.

ФИО и группа подставляются из профиля платформы. Идентификатор учебной работы — существующий `studentKey`, а не введённое в игре имя, код сценария или текущий анонимный Firebase UID. Оболочка курса переведена на RU/EN/ZH. Симулятор и описания критериев доступны на RU/EN; для китайского интерфейса курса недостающие тексты модели показываются на русском.

Преподаватель может открыть пробную кампанию, в том числе при закрытом для студентов разделе, посмотреть расчёт и скачать материалы. Такое прохождение не вызывает запись студенческой попытки или оценки. Его локальные данные находятся в отдельной области `teacher:<uid>`.

## Автоматическая оценка 0–5

Источник формулы и публикуемых пояснений — [`platform-contract.js`](../site/apps/governor/platform-contract.js): `assessmentRules`, `assessCampaign()` и внутренний расчёт `assessReport()`. Расчёт детерминирован для одного и того же состояния и не изменяет игровую модель. Оценивается выполнение задания в симуляторе; это не эмпирически подтверждённая шкала общей профессиональной компетентности.

Обозначим `clip(v) = min(1, max(0, v))`, а долю подтверждённых годовых решений — `c = clip(число записей истории / 20)`. Неисполненный переход не увеличивает число решений. Каждый из пяти исходных критериев ограничен диапазоном 0–1.

| Критерий | Расчёт исходного вклада до поправки на прохождение |
| --- | --- |
| Завершение кампании (`completion`) | `c`: подтверждённые решения из 20. |
| Исполнение программ (`delivery`) | Сумма `clip(implementationFactor)` у запущенных программ с хотя бы одним оплаченным годом, делённая на `max(5, число всех начатых программ)`. Запуск требует `activatedTurn > 0`; оплаченный год — непустого `paidTurns`. Записи `deferred:true`, то есть решения без новой программы, исключаются из числителя и знаменателя. При отсутствии программ вклад равен 0. |
| Услуги в территориях (`territories`) | Среднее 15 нормированных оценок: медицина, школа и занятость в каждой из пяти территорий. Сравниваются исходные и итоговые значения конкретного сценария; точная функция приведена ниже. Отсутствующая пара значений даёт нулевой вклад, знаменатель остаётся 15. |
| Финансовая устойчивость (`finance`) | Среднее нормированного запаса до долгового лимита и доли из трёх прогнозных лет, в которых прогнозная казна плюс текущий резерв неотрицательны. При досрочной передаче финансового управления этот критерий равен 0. |
| Выполнение обещаний (`promises`) | `(выполненные без пересмотра + 0,75 × выполненные после пересмотра) / max(3, число учитываемых обещаний)`. Учитываются все выполненные и нарушенные обещания, а также ожидающие со сроком не позднее 20-го года. Ожидающие за пределами срока исключаются. При отсутствии обещаний вклад равен 0. |

Для территориального показателя исходное `b` и итоговое `x` предварительно ограничиваются диапазоном 0–1:

```text
если b = 1:  s = x
если x < b:  s = 0,5 × x / b
иначе:      s = 0,5 + 0,5 × clip((x − b) / max(0,01; 0,25 × (1 − b)))
```

При `b < 1` сохранение исходной доступности даёт половину исходного вклада. Улучшение на четверть исходного разрыва до 1 даёт полный вклад с учётом минимального знаменателя 0,01. Для исходного `b = 1` действует отдельная ветвь `s = x`. Изменения доступности зависят в том числе от демографии; само сравнение не устанавливает причинный эффект решений студента.

Нормированный долговой запас:

```text
h = clip((текущий лимит − текущий долг) / max(0,01; текущий лимит − начальный долг))
finance = (h + число покрытых прогнозных лет / 3) / 2
```

Берутся только первые три строки прогноза. Для каждой строки проверяется `row.cash + final.reserve >= 0`; один и тот же текущий резерв участвует в каждой проверке. Недостающие строки не увеличивают число покрытых лет. При отсутствии необходимых чисел долговой запас или соответствующий прогнозный вклад равен 0. Прогноз строится моделью без новых проектов и автоматической помощи. При финансовой передаче управления `finance = 0` независимо от прогноза.

Итог формируется последовательно:

1. Первый критерий равен `c`; критерии 2–5 дополнительно умножаются на `c`.
2. Полученные пять составляющих суммируются. Для обычного завершения максимум — 5.
3. При досрочной передаче финансового управления максимум — 2,5. Если сумма выше, **все пять** составляющих пропорционально умножаются на `2,5 / сумма`; иначе множитель равен 1.
4. Итог округляется до 0,01. Сотые составляющих распределяются методом наибольших остатков, при равных остатках — в порядке критериев. Поэтому сумма показанных вкладов точно равна показанной оценке.

Расчёт виден в модуле до завершения как текущий. Итоговая запись создаётся автоматически только для `completed` или `financial-handover`. Последний статус сохраняет фактическое число решений и не выдаётся за полную двадцатилетнюю кампанию.

## Запись результата и журнал

Автосохранение оценки срабатывает при сохранении конечного состояния и при восстановлении уже законченной кампании без локально подтверждённой записи. Ручная отправка не является обязательным шагом; кнопка повторной отправки нужна для восстановления после ошибки. Рефлексия факультативна и сама по себе баллов не добавляет. В фиксируемую попытку попадает текст, подготовленный до её первого сохранения; подтверждённая запись не перезаписывается.

[`makeSubmission()`](../site/apps/governor/platform-contract.js) формирует данные для существующего `backend.saveAttempt()`:

| Поле | Значение или назначение |
| --- | --- |
| `id` | Стабильный `run.submissionId`, повторно используемый при отправке. |
| `studentKey` | Ключ захваченного при запуске владельца `student:<studentKey>`. |
| `source`, `type`, `activitySlug` | `native-v1`, `governor-simulator`, `seminar-7`. |
| `schemaVersion` | `1`. |
| `recordGrade`, `reviewStatus` | `true`, `auto-scored`. |
| `points`, `maxPoints` | Точная `governor.assessment.points` и `5`. |
| `governor.assessment` | Версия формулы, итог, доля прохождения, сумма до ограничения, множитель ограничения и пять критериев с исходным, промежуточным и округлённым вкладом. |
| `governor` | Версии приложения и модели, статус, код и сценарий, конечные показатели, до пяти территорий и до 20 строк решений. |
| `reflection` | Текст учебной рефлексии; мост ограничивает его 6000 символами. |
| `createdAt`, `startedAt`, `durationMs` | Временные метки и неотрицательная длительность. |

Название работы добавляет мост. `ownerUid` и платформенные поля сохранения добавляет существующий backend. Полный файл продолжения игры не помещается в каждую попытку: передаётся компактный отчёт. Единицы в нём сохраняются из модели: доли доступности 0–1, население в людях, денежные показатели в миллиардах модельных рублей. Оболочка умножает доли на 100 только при показе процентов.

На странице семинара видны только нативные отчёты текущего `studentKey`, фактическая оценка каждой попытки и лучшая оценка из backend. В преподавательском журнале отметка «Есть отчёт» открывает расчёт, решения и рефлексию. Эти сведения экранируются при выводе. Сохранённую копию отчёта можно прочитать без сети; изменение оценки по устаревшему снимку отключено.

`backend.saveAttempt()` сначала сохраняет попытку в локальной очереди, затем обновляет локальную лучшую оценку и запускает облачную синхронизацию. Успешное локальное сохранение не равно подтверждённой доставке в облако — интерфейс различает эти состояния.

Существующий принцип лучших результатов сохранён: меньшая новая оценка не понижает старую. Семинар 7 остаётся одной колонкой с максимумом 5; остальные занятия и сумма 100 не меняются. Существующая ручная корректировка преподавателем доступна при необходимости и также следует действующим ограничениям backend. Изменение кода не выполняет миграцию, массовый пересчёт или перезапись старых работ.

## Владельцы, черновики и повторная отправка

[`scopedStorage()`](../site/apps/governor/platform-contract.js) захватывает владельца при создании адаптера. Ключи имеют вид:

```text
rudn.governor.v1:<encodeURIComponent(owner)>:<ключ модуля>
```

Так разделяются основная партия, резервная копия, настройки, достижения, истории жителей, маршрут, метаданные запуска и подготовленная попытка. Имя блокировки записи также зависит от владельца. Неименованные старые сохранения автономного приложения автоматически не подхватываются и не переносятся в профиль.

`createRunMetadata()` создаёт независимые случайные `runId` и `submissionId`. Детерминированный игровой `sessionId`, seed или название сценария не используются как ID попытки: две партии с одним seed остаются разными прохождениями. Метаданные хранятся отдельно от модели и восстанавливаются вместе с текущей кампанией.

Перед первой отправкой мост фиксирует полный подготовленный объект под `submission:<submissionId>`. Повторная попытка отправки использует тот же ID и тот же объект. Облачные попытки студентом не перезаписываются. Новая партия или импорт запускают новые метаданные; они не заменяют ранее завершённую работу.

Общая очередь платформы сохраняет прежние ключи `rudn.pending.v1:<studentKey>:<id>`, локальная копия — `rudn.attempt.v2:<studentKey>:<id>`. Синхронизация обслуживает активного студента и учитывает смену поколения сессии. Выход не удаляет старую очередь и черновики.

При смене владельца, выходе или закрытии доступа к разделу текущая игра блокируется, запись прекращается, блокировка писателя освобождается. Один Firebase UID не является достаточной проверкой: платформа может сохранить анонимный транспорт при выходе студента. На восстановлении страницы из bfcache выполняется перезагрузка, чтобы заново проверить сессию и право записи.

Локальное разделение защищает от случайного смешения профилей в интерфейсе. Оно не заменяет изоляцию браузерного профиля и не меняет существующую модель авторизации платформы. Полная очистка данных сайта удаляет локальные партии и неотправленные результаты; экспорт `.govsave.json` предназначен для переноса партии.

## Общий service worker

За модуль отвечает [`site/service-worker.js`](../site/service-worker.js). Нативный запуск отключает регистрацию собственного вложенного worker симулятора и использует worker родительского курса. В список предварительного кэширования включены обе точки входа (`apps/governor/` и `apps/governor/index.html`), мост, контракт, движок, стили и ресурсы изображения.

Префикс кэша содержит полный scope: `rudn-gmu-pages:<encodeURIComponent(scope)>:`. При активации удаляются только предыдущие кэши этого scope и точно указанный старый кэш платформы `rudn-gmu-pages-v1.2.2`; чужие кэши на том же origin сохраняются. Обработчик не вмешивается в запросы другого origin, пути вне scope и методы, отличные от GET.

HTML и код используют сеть с возвратом к собственной сохранённой копии. Ответы 404/500 не заменяют исправные ресурсы кэша; ошибка записи кэша не отменяет успешный ответ сети. Полная автономная доступность требует успешной установки worker и загрузки его списка ресурсов. Это не означает доступность Firebase без сети.

## Локальные проверки

Контрактные тесты и тесты worker используют Node.js 20+ и запускаются из корня репозитория:

```bash
node --test scripts/test_governor_contract.mjs
node --test scripts/test_governor_service_worker.mjs
node --check site/assets/js/main.js
node --check site/assets/js/teacher-journal.js
node --check site/apps/governor/platform-bridge.js
node --check site/apps/governor/platform-contract.js
git diff --check
```

Контрактные тесты проверяют 14 сценариев: разделение владельцев, уникальность запусков, компактный отчёт, единицы, конечные состояния, точную автоматическую оценку, формулы, ограничения и неизменность входного состояния. Шесть тестов worker проверяют полноту списка ресурсов, изоляцию кэшей, автономный возврат, ответы 404/500, границы scope и ошибку записи кэша. Это локальные проверки с моделированием окружения, а не подключение к действующей базе.

Для ручного просмотра статического сайта:

```bash
python -m http.server 8765 --bind 127.0.0.1 --directory site
```

Откройте [локальную страницу](http://127.0.0.1:8765/). Этот обычный просмотр использует реальную конфигурацию приложения и сам по себе не подменяет авторизацию. Для полностью локального сценария с синтетическими профилями используется отдельный браузерный тест.

При установленном Python Playwright и Chromium:

```bash
python scripts/test_governor_browser.py --output /tmp/rudn-governor-browser-qa
```

Путь вывода должен находиться вне репозитория. При необходимости укажите `--chromium /путь/к/chromium`; параметр `--only` позволяет выбрать сценарии по части имени. Скрипт сам запускает локальный HTTP-сервер с префиксом `/RUDN/`. Только в ответе этого сервера подменяется восстановление backend: синтетические профили, доступ к разделу и недоступный облачный транспорт. Реальные элементы интерфейса, решения игры, локальное сохранение, очередь, вычисление лучшей оценки, Web Locks и service worker остаются рабочими.

После объединения с актуальным карьерным модулем выполнен новый полный браузерный прогон: **10/10**. Подтверждены полные кампании через 20 видимых решений на ПК и телефоне, преподавательское прохождение без записи оценки, разделение владельцев и блокировок, проверка гостя и закрытого раздела, автономное продолжение и возврат в курс, шесть размеров экрана. Общий worker предварительно кэширует **304 URL**. Дополнительно пройден переход преподавателя: раздел 6 → карьерный справочник → раздел 7 → кампания → курс → повторный запуск карьерного модуля. Ошибок JavaScript, консоли и горизонтального переполнения нет. Результаты относятся к реальным DOM, хранилищу, очереди, Web Locks и service worker, с явно синтетическими локальными профилями и отключённым облачным транспортом.

Подмена ограничена локальным восстановлением backend: синтетическая авторизация и недоступный облачный транспорт. Движок, DOM, локальная очередь и сохранения, Web Locks и service worker выполняются в настоящем Chromium. Такой тест не подтверждает реальный вход, права Firebase или доставку результатов в облако; проверка реального входа и облачной доставки остаётся неподтверждённой. История полного прогона и повторов описана в [релизных заметках](RELEASE_NOTES_1.3.1.md).

## Проверки перед публикацией в CI

В [`deploy-pages.yml`](../.github/workflows/deploy-pages.yml) подготовлены последовательные этапы: сборка закреплённого Firebase SDK, проверка статического каталога и синтаксиса, 20 контрактных/worker-тестов, затем полный браузерный прогон. Браузерное окружение использует Python Playwright **1.57.0** и Chromium. Результаты и снимки сохраняются как артефакт `governor-browser-qa` на **7 дней**, в том числе при ошибке проверки.

Этап публикации Pages следует за проверками и не выполняется при их ошибке. Для версии 1.3.1 [выпуск от 11 сентября 2026 года](https://github.com/Arseniy24RUS/RUDN/actions/runs/34642672669) завершился успешно: сборка, статическая проверка, 20 контрактных тестов, 10 браузерных сценариев и развёртывание. HTTPS-проверка опубликованных HTML, main.js и service worker подтвердила ответ 200 и совпадение с проверенной сборкой. Живое браузерное прохождение и вход преподавателя эта проверка не заменяет.
