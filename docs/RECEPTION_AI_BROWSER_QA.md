# Проверка обновлённой «Приёмной»

Актуальный интерфейс состоит из пяти страниц «Приёмная», «Чат», «Документы», «Календарь» и «Решение». Выбор учебной и самостоятельной работы, банка кейсов и сложности находится на стартовой странице. Это выбор задания; переключателя между прежним и новым движком для студента нет.

Проверки разделены по тому, что они действительно измеряют. Модульные тесты проверяют состояния и правила. DOM-сценарий запускает настоящий клиент и серверный сервис с локальным mock-провайдером, включая встроенную читалку. Playwright проверяет геометрию и поведение настоящего браузера. Досье остаются на стороне локального сервера; браузер получает только публичный протокол.

## Выполненная проверка и её пределы

При подготовке мобильного исправления выполнены 15 групп DOM-интеграции на полном банке из 178 кейсов. Проверены каталог и сложность, старт в приёмной с одним непрочитанным сообщением, переходы пяти страниц, чат и документы, ручной календарь, выбор нормы во встроенной читалке, сохранение черновиков и возвращение через другой маршрут платформы. Проверены русский, английский и китайский интерфейсы, изоляция студентов, повтор после потерянного ответа, отказ провайдера, порядок действий, продолжение дела, частично заполненное решение и самостоятельная смена из восьми дел.

Вынос календаря проверяет сохранение выбранной даты, точки отсчёта и ответов о порядке исчисления срока при переходах, смене языка и повторном входе. Итоговый запрос передаёт дату и календарные ответы из общей модели черновика. После фиксации решения календарь остаётся доступен для просмотра без изменения. В простом кейсе без авторской оценочной формы отправка с пропущенным сроком переводит на «Календарь» и фокусирует поле даты; в авторских заданиях пропуски по-прежнему оценивает сервер.

Дополнительно пройдены тесты сохранения сессий и медиа. Для всех 26 персонажей проверены существующие WebM и новые прозрачные animated WebP: 320 пикселей по ширине, 120 кадров, примерно 10 секунд, бесконечный цикл. WebP получены техническим преобразованием исходных анимаций. Общий объём fallback-файлов — 45 815 054 байт; загружается только текущий видимый персонаж, когда видео недоступно. У animated WebP нет интерфейса паузы на текущем кадре: при уходе изображение выгружается, а при возвращении цикл запускается сначала.

Реальная браузерная проверка в среде подготовки не состоялась. Штатный запуск Chromium завершился ошибкой `socket() failed: Operation not permitted` и SIGABRT. Удалённый браузер не имел доступа к локальному стенду. Поэтому DOM-успех не подтверждает отсутствие переполнения на телефоне, фактическое воспроизведение анимаций в Safari или поведение экранной клавиатуры. Сценарий Playwright подготовлен для запуска в обычной среде.

## Проверка выпуска в CI

Workflow `deploy-pages.yml` для выпуска с пометкой `[reception-ai-release]` запускает модульные проверки, DOM-сценарий настоящей читалки и календаря, а затем Playwright на Chromium и WebKit. Для браузерного стенда `scripts/reception-ai-qa-cases.mjs` создаёт временные синтетические досье: приватный учебный банк не попадает в CI и не публикуется. Браузерный сценарий берёт размер каталога из стенда, поэтому проверка трёх синтетических кейсов не подменяет отдельно выполненную проверку банка из 178 кейсов.

Это описание подготовленного gate. Его успешный запуск в CI здесь не наблюдался; снимков интерфейса из данной среды нет. Доказательством браузерной проверки будут результаты конкретного запуска workflow и созданные им отчёты и изображения.

## Модульные и DOM-проверки

Нужны Node.js версии, указанной в package.json, и приватный каталог кейсов вне `site/`.

```bash
node --test firebase/functions/reception-ai/*.test.mjs \
  tests/reception-ai-api-client.test.mjs \
  tests/reception-messenger-media.test.mjs \
  tests/reception-session-storage.test.mjs \
  tests/reception-workbench.test.mjs \
  tests/reception-source-reference.test.mjs
```

DOM-зависимость можно установить отдельно от зависимостей платформы:

```bash
npm install --prefix /tmp/rudn-reception-qa --no-audit --no-fund --ignore-scripts jsdom
node scripts/test-reception-ai-workspace-dom.mjs \
  --cases /absolute/path/private-data/cases \
  --jsdom /tmp/rudn-reception-qa/node_modules/jsdom/lib/api.js \
  --out /tmp/rudn-reception-dom-results
```

`RECEPTION_AI_CASES_DIR` заменяет `--cases`, а `RECEPTION_JSDOM_MODULE` — `--jsdom`. Когда jsdom установлен в обычном пути разрешения модулей Node, отдельный путь не требуется. Прежнее имя `scripts/test-reception-ai-dom.mjs` вызывает этот же актуальный сценарий.

Сценарий использует настоящую оценочную логику только в памяти. Проверка правильного authored-решения читает закрытое досье внутри Node-процесса, не добавляя его в публичные файлы и не отправляя оценок в Firebase. После подтверждения отдельно проверяется продолжение дела: исходное решение и чат заблокированы, итог скрыт до ответа на контрольное действие. Потерянный ответ на сообщение и продолжение повторяется с прежним requestId; повторного вызова провайдера не происходит.

Для воспроизведения выделения настоящим DOM Range и переноса точной статьи используется дополнительный сценарий:

```bash
node scripts/test-reception-workbench-dom.mjs \
  --jsdom /tmp/rudn-reception-qa/node_modules/jsdom/lib/api.js
```

## Playwright с изолированным стендом

Основная команда самостоятельно поднимает локальный mock-сервис и закрывает его после проверки. Она не обращается к Firebase или OpenAI.

```bash
node scripts/test-reception-ai-workspace-browser.mjs \
  --cases /absolute/path/private-data/cases \
  --playwright-module /absolute/path/node_modules/playwright/index.mjs \
  --out /tmp/rudn-reception-browser-results
```

Если Playwright ещё не установлен, его можно подготовить в отдельной папке:

```bash
npm install --prefix /tmp/rudn-reception-browser-tools playwright
/tmp/rudn-reception-browser-tools/node_modules/.bin/playwright install chromium
node scripts/test-reception-ai-workspace-browser.mjs \
  --cases /absolute/path/private-data/cases \
  --playwright-module /tmp/rudn-reception-browser-tools/node_modules/playwright/index.mjs
```

`--browser webkit` выбирает установленный WebKit. `--executable` задаёт путь к браузеру, `--headed` открывает его окно. Для пути к Playwright также поддерживается `RECEPTION_PLAYWRIGHT_MODULE`. Все параметры доступны через `--help`; прежнее имя `scripts/test-reception-ai-browser.mjs` является точкой входа в этот же сценарий.

Для ручного осмотра можно запустить стенд отдельно:

```bash
node scripts/reception-ai-workspace-qa.mjs \
  --cases /absolute/path/private-data/cases --port 8793
```

Страница открывается по адресу `http://127.0.0.1:8793/__qa/reception.html`. Во втором терминале её можно проверить командой:

```bash
node scripts/test-reception-ai-workspace-browser.mjs \
  --url http://127.0.0.1:8793 \
  --playwright-module /absolute/path/node_modules/playwright/index.mjs
```

Параметр `--url` предназначен для нового workspace-стенда. Обычный `reception-ai-dev.mjs` остаётся инструментом разработки API, но не предоставляет проверочную оболочку платформы и маршрут `/__qa/health`. Это проверяется до запуска браузерного сценария.

## Содержание браузерного сценария

Сначала проверяется локальный mock-провайдер, полный каталог и фильтр сложности. Затем запускается заранее выбранный учебный кейс. Приёмная должна показывать персонажа и badge «1» на чате; пять страниц доступны из собственной панели, а общая мобильная панель платформы скрыта.

После диалога открываются материалы и встроенный нормативный документ. Выбор параграфа переносится в решение, ручная дата из отдельной вкладки «Календарь» — в общее поле срока решения. В «Решении» остаётся сводка срока со ссылкой на календарь, а дата нормативного акта сохраняется среди реквизитов правового основания. Переходы между страницами и выход в проверочную оболочку с последующим возвращением должны сохранять sessionId, переписку, неотправленное сообщение, основание и решение.

На ширинах 320, 360 и 390 CSS-пикселей проверяется отсутствие горизонтального переполнения на каждой из пяти страниц. Все пять пунктов собственной панели должны вмещаться по ширине и иметь доступную область нажатия; проверяются и подписи, и иконки. В чате поле и кнопка отправки должны находиться выше собственной нижней панели и оставаться доступными для нажатия. Отдельно проверяется укороченный viewport 390 × 460. Такой viewport не заменяет экранную клавиатуру настоящего телефона.

В отдельном проходе браузер моделирует отсутствие VP9: клиент должен загрузить WebP текущего персонажа шириной 320 пикселей. Проверяется RIFF/WEBP, 120 кадров ANMF и бесконечный цикл, затем освобождение изображения при уходе в чат и при уменьшенном движении. Проверка файла и его загрузки не выдается за наблюдение движения кадров.

Состояние медиа фиксируется фактически: декодируемое и воспроизводящееся видео, загруженный WebP либо статический резервный портрет. Загрузка WebP сама по себе не считается наблюдением кадров анимации. При `prefers-reduced-motion` видео должно быть остановлено.

После настоящего выполнения создаются `report.json` и снимки экранов. При ошибке запуска браузера снимков интерфейса не будет. Проверочная оболочка использует настоящий клиент, стили, документы и графику, но не заменяет проверку маршрута в авторизованной рабочей платформе. Перед занятием требуется проверить штатный вход, возврат, звук/беззвучный режим, экранную клавиатуру, уменьшенное движение и анимацию на доступных телефонах iOS и Android.
